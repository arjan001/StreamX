1. OVERVIEW
================================================================================

The logging system has two layers:

  A) CLIENT-SIDE DEBUG LOG BUFFER (debugLog.ts)
     - Captures all errors, warnings, and info messages in memory
     - Ring buffer of 400 entries, dies with the page
     - Intercepts console.error, console.warn, uncaught exceptions,
       unhandled promise rejections, failed HTTP fetches, offline/online events
     - Provides dlog.info(), dlog.warn(), dlog.error() for manual logging
     - Does NOT write to disk or send to server by itself

  B) AUTOMATIC ERROR REPORTER (errorReports.ts)
     - Subscribes to the debug log buffer
     - Filters, folds duplicates, and batches errors
     - Sends batches to server every 3 minutes via POST /api/log/batch
     - OFF by default; enabled by server admin config or beta APK builds

  C) SERVER-SIDE LOG HANDLER (log.ts)
     - Receives logs via two POST endpoints
     - Redacts credentials (double-layered with client)
     - Rate-limits per device (60 rows per minute)
     - Stores in PostgreSQL client_log table
     - Auto-purges logs older than 7 days

  D) ADMIN PANEL (admin.ts)
     - Provides GET /api/admin/logs to view all stored logs
     - Supports filtering by level, search text, device ID prefix
     - Groups logs by first 90 characters of message
     - Shows count, distinct devices, and affected builds

2. DATABASE SCHEMA
================================================================================

Database: PostgreSQL

--- TABLE: client_log ---

CREATE TABLE IF NOT EXISTS client_log (
  id          bigserial PRIMARY KEY,
  at          timestamptz NOT NULL DEFAULT now(),
  device_id   text        NOT NULL,
  level       text        NOT NULL DEFAULT 'error',
  message     text        NOT NULL,
  context     jsonb,
  app_version text,
  platform    text
);

CREATE INDEX IF NOT EXISTS ix_client_log_at ON client_log (at DESC);
CREATE INDEX IF NOT EXISTS ix_client_log_device ON client_log (device_id, at DESC);

Column Descriptions:
  id          - Auto-incrementing primary key
  at          - Timestamp when the log was received by the server (server time)
  device_id   - Random 24-char ID generated at app launch (NOT persistent)
  level       - Log level: "error", "warn", or "info"
  message     - Redacted log text, prefixed with tag (e.g. "player: ...")
                Max 2000 characters
  context     - JSONB object with additional data:
                - auto: true (for automatic reports)
                - tag: source component name
                - count: how many times this error occurred (repeats folded)
                - agoSeconds: seconds since first occurrence
                - device: device summary object (build, platform, etc.)
  app_version - App version string (e.g. "1.64.1" or "1.64.1+build123")
  platform    - Platform identifier: "android-app" or "web"

Retention Policy:
  - Logs older than 7 days are automatically deleted
  - Purge runs hourly and after each write (at most once per hour)
  - Admin can manually truncate the entire table via POST /api/admin/reset

--- TABLE: app_config ---

CREATE TABLE IF NOT EXISTS app_config (
  id         integer PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  revision   bigint      NOT NULL DEFAULT 1,
  updated_at timestamptz NOT NULL DEFAULT now(),
  payload    jsonb       NOT NULL DEFAULT '{}'::jsonb
);

The app_config table stores operator-configurable settings including:
  - errorReports: boolean — enables/disables automatic error reporting
  - minVersion: string — minimum allowed app version
  - updateMessage: string — update notification message
  - notice: string — maintenance notice for all users
  - deviceRelayOff: boolean — disable Android TV relay
  - localCatalogueDefault: boolean — default catalogue setting

3.1 POST /api/log
--------------------------------------------------------------------------------
Purpose: Single manual debug report (user-triggered from debug panel)

Request Body (JSON):
{
  "deviceId": "abc123def456...",        // Required: 24-char launch ID
  "level": "info",                       // Optional: "error", "warn", "info"
  "message": "debug report: last error", // Required: redacted text (max 2000 chars)
  "context": {                           // Optional: JSON object (max 4000 chars)
    "device": { "Build": "1.64.1", ... },
    "lines": ["12:34:56.789 E player: ..."]
  },
  "version": "1.64.1",                   // Optional: app version string
  "platform": "android-app"              // Optional: "android-app" or "web"
}

Response (200 OK):
{ "ok": true }

Response (202 Accepted — rate limited):
{ "ok": true, "dropped": true }

Response (400 Bad Request):
{ "error": "bad request" }

3.2 POST /api/log/batch
--------------------------------------------------------------------------------
Purpose: Automatic batch error reports (sent every 3 minutes by client)

Request Body (JSON):
{
  "deviceId": "abc123def456...",        // Required: 24-char launch ID
  "accountId": "user123",               // Optional: user's account ID from session
  "entries": [                           // Required: array of error entries
    {
      "tag": "player",                  // Source component
      "text": "Playback failed: ...",   // Redacted error text
      "level": "error",                 // "error", "warn", "info"
      "count": 3,                       // How many times this occurred
      "ago": 120                        // Seconds since first occurrence
    }
  ],
  "device": {                            // Optional: device summary
    "Build": "1.64.1",
    "Running as": "installed app",
    "Native engine": "libVLC present",
    "Web engine": "Chromium 120",
    "Device": "Samsung QN90A",
    "Decoders": "OMX.SEC.AVC.Decoder",
    "Viewport": "3840x2160 @1x",
    "Origin": "https://yourdomain.com",
    "Online": "yes"
  },
  "version": "1.64.1",                   // Optional: app version
  "platform": "android-app"              // Optional: platform
}

Response (200 OK):
{ "ok": true, "stored": 5 }

Response (202 Accepted — rate limited):
{ "ok": true, "stored": 0, "dropped": 5 }

Response (400 Bad Request):
{ "error": "bad request" }

Batch limits:
  - Max 30 entries per batch
  - Max 60 rows per device per minute (rate limited)
  - Each message max 2000 characters
  - Context JSON max 4000 characters

4. CLIENT-SIDE LOGGING ARCHITECTURE
================================================================================

File: apps/web/src/lib/debugLog.ts

The debug log is the central capture point for all errors and warnings.

--- Ring Buffer ---
  - Capacity: 400 entries
  - Each entry: { id, timestamp, level, tag, text }
  - Lives in memory only, dies with the page
  - Every line redacted on entry (max 600 chars per line)

--- Automatic Capture ---
  installDebugCapture() hooks the following:

  1. console.error → tag: "console", level: "error"
  2. console.warn   → tag: "console", level: "warn"
  3. Uncaught exceptions → tag: "page", level: "error"
  4. Unhandled promise rejections → tag: "page", level: "error"
  5. Failed HTTP fetches → tag: "fetch", level: "error"
  6. HTTP non-OK responses → tag: "fetch", level: "warn"
  7. Window offline → tag: "net", level: "warn"
  8. Window online → tag: "net", level: "info"
  9. App boot info → tag: "boot", level: "info"

--- Manual Logging API ---
  import { dlog } from './debugLog.ts';

  dlog.info('catalogue', 'Channel list refreshed: 55000 channels');
  dlog.warn('catalogue', 'Channel list refresh skipped');
  dlog.error('player', 'Playback failed: decoder refused');

--- Device Summary ---
  deviceSummary() returns key-value pairs:
  - Build: "1.64.1+build123"
  - Running as: "installed app" or "browser"
  - Native engine: "libVLC present" or "none — WebView only"
  - Web engine: "Chromium 120"
  - Device: "Samsung QN90A" (if detectable)
  - Decoders: "OMX.SEC.AVC.Decoder, c2.android.avc.decoder"
  - Viewport: "3840x2160 @1x"
  - Origin: "https://yourdomain.com"
  - Online: "yes" or "no"

--- Launch ID ---
  launchId() generates a random 24-character ID at app launch.
  This ID is NOT persistent across restarts. It is used for:
  - Rate limiting on the server
  - Grouping logs from the same app session

5. ERROR REPORTING FLOW (AUTOMATIC)
================================================================================

File: apps/web/src/lib/errorReports.ts

--- When It Runs ---
  - OFF by default
  - Enabled when server app-config returns errorReports: true
  - ALWAYS ON in beta APK builds (native + non-empty build number)
  - Re-read when app comes to foreground (no restart needed)

--- The Flow ---

  1. CAPTURE
     debugLog.ts pushes every error/warn to errorWatchers
     → errorReports.ts noteError() receives the entry

  2. FILTER
     reportable() drops:
     - Empty messages
     - Messages containing "/api/log" (prevents infinite loop)
     - Tag "fetch" (raw HTTP noise)
     - Player door attempts, retries, EPG probe requests
     - Warnings from non-critical tags

  3. FOLD
     signature() normalizes each error:
     - Strips query strings
     - Replaces numbers with "#"
     - Collapses whitespace
     - Takes first 160 chars
     Same signature = same error → count incremented

  4. QUEUE
     - Max 30 distinct errors in queue
     - Resend cooldown: 30 minutes per signature
     - Queue starts flush timer on first error

  5. FLUSH
     - Timer: 3 minutes (180,000ms) from FIRST error
     - Sends POST /api/log/batch with all queued entries
     - On app close (pagehide), uses navigator.sendBeacon() for final flush
     - Failed flush is dropped (not re-queued) to prevent memory growth

--- What Each Log Carries ---
  - deviceId: random 24-char launch ID
  - accountId: user's account ID from current session (for per-user tracking)
  - entries: array of { tag, text, level, count, ago }
  - device: device summary object
  - version: app version string
  - platform: "android-app" or "web"

6. MANUAL DEBUG REPORT FLOW
================================================================================

File: apps/web/src/lib/debugLog.ts → sendDebugReport()

When a user manually triggers a debug report (from the debug panel):

  1. Takes last entries from ring buffer (newest first)
  2. Packs into context JSON (max 3400 chars)
  3. Sends POST /api/log with:
     - deviceId: launch ID
     - level: "info"
     - message: "debug report: <last error text>"
     - context: { device: {...}, lines: [...] }
     - version: app version
     - platform: "android-app" or "web"

This is different from automatic reporting:
  - Carries the full debug buffer, not just errors
  - Sent as "info" level, not "error"
  - User-triggered, not automatic

7. LOG TAGS AND WHAT THEY CAPTURE
================================================================================

Each log entry has a "tag" that identifies its source component.

Tag: "signin" (File: session.ts)
  - Login attempts: username, server hostname
  - Login success: account ID (partial), username, server hostname, subscription expiry
  - Login failure: username, server hostname, reason, error message
  - No host found: reason, number of hosts tried, each host's verdict

Tag: "player" (File: playerCore.ts)
  - Playback failures: error message, hint, trail of attempts

Tag: "catalogue" (File: localCatalogue.ts)
  - Library build failure: error message
  - Storage full, switching to on-demand mode
  - Host switch during download
  - Channel list refresh: skipped, failed, or success with count
  - Portal list truncated: size limit reached
  - Channel names compared: number of renamed channels
  - Channel logos stored: wanted, queued, removed counts

Tag: "boot" (File: debugLog.ts)
  - App boot: device summary (build, platform, native engine, Chromium, device, decoders, viewport, origin, online)
  - User agent string

Tag: "console" (File: debugLog.ts)
  - All console.error output from libraries
  - All console.warn output

Tag: "page" (File: debugLog.ts)
  - Uncaught exceptions: error message, file, line number
  - Unhandled promise rejections: rejection reason

Tag: "fetch" (File: debugLog.ts)
  - Failed HTTP requests: error, URL, response time
  - HTTP non-OK responses: status code, URL, response time
  (Note: "fetch" tag is filtered out by errorReports.ts — not sent automatically)

Tag: "net" (File: debugLog.ts)
  - Offline/online connection status changes

Tag: "native" (File: deviceInfo.ts, nativeBridge.ts)
  - Native engine probe: libVLC available or not
  - Last crash reason from previous run
  - Native bridge communication errors

Tag: "epg" (File: bulkGuide.ts)
  - Bulk guide downloaded: programme count, channel count, data size
  - Bulk guide failed: failure reason

Tag: "captions" (File: liveCaptions.ts)
  - Native audio probe: whether native audio listening works

Tag: "field" (File: debugLog.ts)
  - Keydown events in input fields: key, code, keyCode, composing state, repeat, field name
  - Password field values are redacted

Tag: "update" (Various)
  - App update-related events

Tag: "perf" (Various)
  - Performance-related warnings

8. CREDENTIAL REDACTION
================================================================================

All logs are redacted TWICE — once on the client and again on the server.

--- Client-Side Redaction (debugLog.ts) ---
  Strips from every log line:
  - Query parameters: username=, password=, pass=, user=, token=, mac=,
    sn=, serial=, device_id=, key=, auth=, signature=
  - Percent-encoded variants of the above
  - URL authority: //user:pass@host
  - Xtream path credentials: /live/user/pass/id.ext
  - MAC addresses (both : and %3A separated)
  - Bearer tokens
  - Cookie and Authorization header lines
  - JSON body secrets: "username": "value"

--- Server-Side Redaction (log.ts) ---
  Same rules applied again on arrival. Belt and braces: if one layer is
  wrong, the other catches it.

--- Field-Level Redaction ---
  Password input fields are redacted at the keydown level:
  - Single characters in password fields show as "<char>"
  - keyCode in password fields shows as "<redacted>"
  - Unknown keys in password fields are redacted (fail closed)

9. RATE LIMITING AND RETENTION
================================================================================

--- Rate Limiting (Server-Side) ---
  - 60 rows per device_id per 60-second window
  - Counted in ROWS, not requests (batch of 30 = 30 rows)
  - When exceeded: returns 202 with { ok: true, dropped: true }
  - Not 429: a failing client should not also handle being told off
  - In-memory tracking map, bounded at 5000 entries

--- Client-Side Limits ---
  - Max 30 distinct errors per flush queue
  - Resend cooldown: 30 minutes per error signature
  - Flush interval: 3 minutes from first error
  - Fetch noise filtered out (no raw HTTP errors sent)

--- Retention ---
  - 7-day retention: logs older than 7 days are deleted
  - Purge runs hourly and after each write (at most once per hour)
  - Admin can manually truncate via POST /api/admin/reset

10. CONFIGURATION
================================================================================

--- Server-Side Configuration ---

Environment Variables:
  ADMIN_USERNAME - Admin panel username (default: "admin")
  ADMIN_PASSWORD - Admin panel password (if not set, admin is DISABLED)

Database:
  - PostgreSQL connection via apps/server/src/db/pool.ts
  - Tables created by apps/server/src/db/alters.sql
  - Run alters.sql against your PostgreSQL database to create the tables

App Config (stored in app_config table, modified via admin panel):
  errorReports: true/false — enables/disables automatic error reporting
  minVersion: "1.64.0" — minimum allowed app version
  updateMessage: "Please update" — update notification text
  notice: "Maintenance at midnight" — notice shown to all users
  deviceRelayOff: true/false — disable Android TV relay
  localCatalogueDefault: true/false — default catalogue setting

--- Client-Side Configuration ---

Environment Variables (Vite/Capacitor build):
  VITE_API_ORIGIN - Server URL for API calls
    - Web builds: leave empty (uses same-origin relative paths)
    - Capacitor/APK builds: set to your server URL
      e.g., "https://yourdomain.com"
  VITE_APP_VERSION - App version string
  VITE_APP_BUILD - Build number (triggers beta mode if non-empty on native)
  VITE_PLATFORM - "capacitor" for native builds, undefined for web

Beta Mode:
  - Automatically enabled when: NATIVE build AND non-empty BUILD number
  - In beta mode, error reports are ALWAYS ON regardless of server config
  - This allows the client/developer to see all user logs automatically

11. ADMIN PANEL INTEGRATION
================================================================================

The admin panel provides a web interface for viewing and managing logs.

--- Accessing Logs ---
  1. Login via POST /api/admin/login
  2. Use returned token in x-admin-token header
  3. Fetch logs via GET /api/admin/logs?level=error&q=player&page=0&size=50

--- Log Grouping ---
  Logs are grouped by the first 90 characters of the message. This means:
  - Same error from different devices appears in one group
  - Each group shows: count, distinct devices, newest occurrence, builds

--- Filtering ---
  - level: filter by "error", "warn", "info", or "all"
  - q: full-text search on message and app_version (ILIKE)
  - device: prefix match on device_id

--- Enabling Error Reports ---
  Via admin panel: PUT /api/admin/config
  {
    "revision": <current_revision>,
    "config": { "errorReports": true }
  }

  Or via database directly:
  UPDATE app_config SET payload = '{"errorReports": true}'::jsonb
  WHERE id = 1;

12. HOW TO SET LOG SERVER URL (WEB AND APK)
================================================================================

This is the most important section for integrating log posting with a
custom server URL.

--- Option A: Same-Origin (Web Deployment) ---

If your web app and API server are on the same domain:

  VITE_API_ORIGIN: (leave empty or unset)

  The app will use relative paths like "/api/log/batch" which resolve
  to the same origin as the web page.

  Example:
    Web served from: https://yourdomain.com/app/
    API at: https://yourdomain.com/api/log/batch
    → Works automatically, no configuration needed

--- Option B: Custom Server URL (Capacitor/APK Builds) ---

For APK builds (Capacitor), the app loads from file:// or capacitor://
which cannot use relative paths. You MUST set VITE_API_ORIGIN:

  In vite.config.ts or .env:
    VITE_API_ORIGIN=https://yourdomain.com

  The app will then send logs to:
    https://yourdomain.com/api/log/batch

--- Option C: Separate Log Server ---

If you want logs to go to a DIFFERENT server than your main API:

  The current code uses a single ORIGIN for all API calls. To send logs
  to a separate server, you would need to modify errorReports.ts to use
  a different base URL for /api/log/batch calls.

  Alternative: Deploy the same log.ts endpoints on your separate server
  and set VITE_API_ORIGIN to that server's URL.

--- APK Build Configuration ---

For Capacitor APK builds, the VITE_API_ORIGIN is set at build time.
Check your build configuration:

  apps/web/vite.config.ts — look for apiOrigin setting
  apps/android/ — Capacitor Android project

  To change the server URL for an existing APK build:
  1. Set VITE_API_ORIGIN in your build environment
  2. Rebuild the APK

  Example build command:
    VITE_API_ORIGIN=https://yourdomain.com pnpm build

--- Verifying Log Endpoint ---

To test that logs are being sent correctly:

  1. Open the app and trigger an error (e.g., try to play a bad stream)
  2. Wait 3 minutes for automatic flush
  3. Check server logs for POST /api/log/batch
  4. Or check admin panel: GET /api/admin/logs

  For manual testing, you can also send a test log:

    curl -X POST https://yourdomain.com/api/log \
      -H "Content-Type: application/json" \
      -d '{
        "deviceId": "test123456789012",
        "level": "info",
        "message": "Test log from curl",
        "context": {"test": true},
        "version": "1.64.1",
        "platform": "web"
      }'

================================================================================
14. EXTENDING THE SYSTEM
================================================================================

--- Adding a New Log Tag ---

1. Choose a tag name (e.g., "search", "favourites", "settings")
2. In your component file:

     import { dlog } from './lib/debugLog.ts';

     dlog.info('search', 'Search completed: 42 results for "action"');
     dlog.error('search', 'Search failed: dictionary not built');

3. If you want warnings from this tag sent automatically, add it to
   WARN_TAGS in errorReports.ts:

     const WARN_TAGS = new Set(['player', 'native', 'signin', 'catalogue',
                                'captions', 'update', 'perf', 'search']);

--- Adding IP Address Tracking ---

Currently, the server does NOT capture client IP addresses in log entries.
To add this:

1. Modify log.ts POST /api/log and POST /api/log/batch handlers
2. Add req.ip to the context JSON or a new column
3. Update the database schema if needed

--- Adding User Activity Tracking ---

Currently, the system tracks ERRORS only, not user activity. To add analytics:

1. Create a new endpoint (e.g., POST /api/analytics)
2. Add a new table (e.g., user_activity)
3. Create a client-side analytics module similar to errorReports.ts
4. Consider privacy implications and consent mechanisms

--- Adding Streaming Quality Metrics ---

To track buffering ratio, bitrate, resolution, quality switches:

1. Extend the player's error/info logging to include quality data
2. Add new fields to the context JSON in batchRows()
3. Update the admin panel to display quality metrics
